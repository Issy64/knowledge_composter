# Knowledge Input (ナレッジインプット) ワークフロー

ユーザーが「単語（例：Docker）」や「〇〇について」とチャットに入力し、インプット（堆肥化）モードがトリガーされた場合は、必ず以下のステップに従って対話的に処理を進めてください。

## 登録フロー

### Step 1: 単語の確認と重複調査
1. ユーザーが入力した単語を受け付けます。
2. `data.json` を読み込み、同じ単語または類似する単語が既に登録されていないかを調査します。
3. **重複・類似単語が存在した場合のルール**:
   - 既存の単語がどのような意味（WHAT/HOW）で登録されていたかをユーザーに提示し、確認します。
   - もし同じ意味で再登録しようとしていた場合、単語の新規追記は行わず、既存の単語の `status` を以下のように更新します。
     - 現在のステータスが `new` の場合 → `new` のまま（変更なし）
     - 現在のステータスが `learned` または `reviewing` の場合 → `reviewing` に変更（ユーザーが忘れている可能性があるため）
   - 別の意味での登録を意図していた場合は、別エントリとして登録を進めます。

### Step 2: 単語の意味の調査・記述内容の提案
重複がない（あるいは別の意味で新規登録する）場合、単語の意味を調査します。
1. **先入観の排除**: これまでのコンテキストから「IT用語」と決め打ちせず、一般的な意味、ビジネス用語、IT用語など、複数のドメインでの意味をフラットに検討します。
2. **提案の作成**: `data.json` に登録するための「端的な意味（WHAT）」と「実践での使い方や具体例（HOW）」のドラフトを作成します。
   - 複数の意味が考えられる場合は、代表的なものを複数提示し、ユーザーにどれを登録すべきか選択を促します。
   - HOW（使い方）は辞書的な説明ではなく、「ユーザーがどのようなシチュエーションでその概念を使うか・遭遇するか」を具体的に記述します。

### Step 3: ユーザーの確認・承認
Step 1（重複時の確認）または Step 2（提案内容の確認）の結果をユーザーに提示し、「この内容で登録（更新）して良いか」を質問します。
ユーザーから「OK」「それで良い」といった承認を得るまで、絶対に `data.json` への書き込みを行わないでください。

### Step 4: JSON記述
ユーザーからの承認を得た後、`data.json` を更新します。
- 新規登録の場合: `status: "new"` として配列の最後に追記します。
- 重複更新の場合: Step 1のルールに従って対象要素の `status` を更新します。

### Step 5: コミット
更新完了後、`git-commit-convention` スキルに従い、適切なプレフィックス（`feat(knowledge):` や `docs(knowledge):` など）と詳細なDescriptionを添えてコミットを作成します。
